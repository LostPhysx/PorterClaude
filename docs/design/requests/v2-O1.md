## 1. To B2 (`server/src/sessions/container.ts`) — overriding the entrypoint DROPS the image CMD

`orchestration.md` §12 says: *entrypoint `["<toolsMount>/entrypoint.sh"]` for every session;
`cmd ["sleep","infinity"]` only for custom images (**recipes keep their image CMD**)*. The
engine does not work that way: when `Config.Entrypoint` is set in `POST /containers/create`
and `Config.Cmd` is empty, the image's `Cmd` is **not** inherited.

Measured on the reference host with `nginx:alpine` (same shape as the php recipe:
`ENTRYPOINT` + a real `CMD`):

```
create {Entrypoint:["/opt/porterclaude/entrypoint.sh"]}  (no Cmd)
  -> container Config.Cmd = null          image Config.Cmd = ["nginx","-g","daemon off;"]
  -> pid 1 is entrypoint.sh, which idles; nothing listens on port 80
create {Entrypoint:["/opt/porterclaude/entrypoint.sh"], Cmd:["nginx","-g","daemon off;"]}
  -> nginx master + workers run, http://127.0.0.1/ serves the page
```

So the **server must copy the image's own CMD into the create body** whenever it overrides
the entrypoint:

* inspect the image (`GET /images/<ref>/json` → `.Config.Cmd`; both backends already expose
  an inspect) and pass that as `Cmd`;
* fall back to `["sleep","infinity"]` when the image declares no `Cmd` (that is the custom
  image case and stays exactly as designed);
* the php recipe is the one that breaks silently otherwise: the container comes up, the
  terminal works, and only the published port is dead — QA plan item 15.

`entrypoint.sh` itself needs no change: it already `exec "$@"`s whatever CMD it is given and
idles when there is none (and when the command is literally `sleep infinity`).

> **RESOLVED (build doctor).** `resolveImage()` now returns `ImageInspect.cmd` alongside the
> image PATH and `buildContainerSpec` takes it as `imageCmd`: recipes are created with their
> own CMD repeated verbatim, an image without one and every custom image keep
> `["sleep","infinity"]`. Recomputing the spec of an existing container reads the Cmd back
> from `ContainerInspect.cmd` (added to the backend type, mapped in the shared
> `toContainerInspect`), so the spec hash round-trips instead of flapping — a container
> created before the fix reports `needsRecreate`, which is what it needs. Covered by unit
> tests in `container.test.ts` (incl. the hash) and a create-path test in
> `sessionService.test.ts`; `backend.md` §"Delivery is uniform" now states the real engine
> rule. Not re-measured live — the fix restores exactly the second create body above.

## 2. To B2 — what the tools sync now looks like from the outside (all confirmed on arm64)

* A fresh sync of `claude` + `gemini` (script + npm) took **34 s**; a re-sync in which both
  are carried over took **6 s**; a forced full reinstall (`PORTERCLAUDE_TOOLS_FORCE=1`)
  again ~33 s. Please keep the job timeout generous anyway: `aider` (pip) pulls a uv CPython
  plus ~250 MB of wheels, and a cold `apt` layer for the image build comes on top.
* Payload size after `claude` + `gemini`: ~640 MB (the two claude binaries are ~290 MB each,
  Node ~60 MB). That is one volume per host — worth a line in the UI/docs (O2).
* `<toolsMount>/VERSION` now holds the **first line of `claude --version`**, i.e.
  `2.1.224 (Claude Code)`, because the driver probes the installed agent through its shim
  instead of trusting the requested channel. `AGENTS.json` carries the identical string in
  `agents[].version`. If `ToolsStatus.claudeVersion` should be the bare `2.1.224`, strip in
  the server — the image side deliberately does not guess at an agent's version format.
* `PORTERCLAUDE_AGENTS` is validated with `jq` before anything is written: a malformed spec
  (or an `id` that is not a slug, an unknown `install.kind`, an empty `versionCommand`) exits
  **2** and the volume is untouched. A single agent failing is exit **0** with
  `installed:false` + a one-line `error` — that is the normal degraded state.
* A command collision (two enabled agents with the same `command`) is resolved first-wins;
  the loser is still installed but gets `error: "command 'x' is already provided by agent
  'y'"`. If the UI wants to prevent that, it must do so at enable time.
* Passing `PORTERCLAUDE_TOOLS_MOUNT` is still only *recommended*; the default
  (`/opt/porterclaude`) is what the installer bakes when it is absent.
* The ETXTBSY rule holds in practice: with a `node` from the volume running inside a session,
  a forced re-sync finished with exit 0, no `ETXTBSY`, the running process kept its (now
  unlinked) inode, and newly started agents used the new tree.

## 3. To B2 — the root bootstrap exec is load-bearing for recipe (uid 1000) sessions

Confirmed by simulating a uid-1000 session on a fresh auth volume:

* before the server's root exec, `sh -c claude` works (the container `PATH` carries
  `<toolsMount>/bin`) but `sh -lc claude` does **not**: a login shell runs `/etc/profile`,
  which resets `PATH`, and a non-root session cannot write `/etc/profile.d/porterclaude.sh`
  or `/usr/local/bin/<command>`;
* after `chown -R <uid>:<gid> <containerHome>/.porterclaude` **and**
  `<toolsMount>/entrypoint.sh --porterclaude-bootstrap` as root, the profile snippet and the
  `/usr/local/bin` wrappers exist, the agent symlinks are created and `sh -lc claude
  --version` prints the version.

Terminals open login shells, so the bootstrap exec must complete before (or the terminal must
be opened after) the first terminal — exactly what `backend.md` §13 describes. No change
requested, just don't drop it.

## 4. To O2 (`docs/AGENTS.md`, `docs/DEPLOYMENT.md`) — two facts worth documenting

1. **npm agents on musl (alpine) need `libgcc`/`libstdc++`.** The unofficial musl build of
   Node is dynamically linked against them and a bare `alpine:3.20` ships neither. The
   bundled dispatcher now prints
   `porterclaude: the musl build of node needs libgcc/libstdc++, which this image does not
   ship. On alpine: apk add --no-cache libstdc++ libgcc`
   before the loader's own error. `claude` itself is unaffected (its musl build is static and
   was verified working in an `alpine:3.20` session).
2. **pip agents are glibc only** — the generated launcher exits with
   `porterclaude: <agent> requires a glibc image on this host.` instead of a loader error.

## 6. To the planner (`docs/design/orchestration.md` §14.3) — the file seed rule is wrong for YAML

Fix round 1, finding **OPS-2**. §14.3 currently says:

> for `kind=file`, seed `source` when absent — `{}` when its name ends in `.json`, otherwise
> an empty file

An empty file is not a neutral default for a structured config. The built-in `aider` shares
`~/.aider.conf.yml` (`kind: file`), configargparse loads it as YAML, and a zero-byte file
makes every session fail with

```
aider: error: The config file doesn't appear to contain key: value pairs …
yaml.load(/home/dev/.aider.conf.yml) returned type NoneType instead of dict   (exit 2)
```

`entrypoint.sh` therefore now seeds `{}` for `*.json`, `*.yml` **and** `*.yaml` (`{}` is the
empty mapping in JSON and in YAML, JSON being a YAML subset) and repairs an *existing*
zero-byte source with those suffixes on the next start, so auth volumes seeded by an earlier
build heal themselves. Everything else still gets a zero-byte file, and a non-empty source is
never touched. Please restate §14.3 bullet 1 as:

> for `kind=file`, seed `source` when absent — `{}` when its name ends in `.json`, `.yml` or
> `.yaml`, otherwise an empty file; a *pre-existing* zero-byte `.json`/`.yml`/`.yaml` source
> is rewritten to `{}` (it carries no user data)

Verified on the reference host (Portainer, arm64) with `claude` + `aider` enabled and a
`debian:bookworm-slim` session: both `aider.conf.yml` and `aider.model.settings.yml` in
`pc-o1-auth-aider` contain `{}`, `aider --version` → `aider 0.86.2` (exit 0),
`claude --version` → exit 0. `{}` is also safe for `~/.aider.model.settings.yml`, which aider
iterates (`for model_settings_dict in model_settings_list`) — an empty mapping yields no
iterations, checked against the installed `aider/models.py:1070`.

`server/src/agents/builtin.ts` needs **no** change: the aider definition (two `file` shared
paths ending in `.yml`) is correct as written, and the same rule now covers any future agent
with a YAML config. Documented in `docker/tools/README.md` ("Seeding the shared paths") and
`docker/README.md`.

## 7. Fix round 2 (OPS-3) — `force` is now the AGENT UPGRADE switch (files I do not own)

An installed agent could never be updated: `install-agents.sh` carries an agent over whenever
its `SPEC.json` is unchanged, and a spec does **not** change when upstream ships a new release.
`PORTERCLAUDE_TOOLS_FORCE=1` (the documented off switch for the carry-over) was never set by
the server — not even for `{"force":true}`, which only rebuilt the image. Fixed at the root:

* **`server/src/images/service.ts` (B2)** — `syncTools` now passes
  `PORTERCLAUDE_TOOLS_FORCE=1` into the populate container when `force` is true (new local
  const `TOOLS_FORCE_ENV`, next to `TOOLS_AGENTS_ENV`), logs
  `forced: every agent is reinstalled from source (no carry-over)`, and the method comment
  states that `force` is the agent upgrade path. Nothing else changed.
* **`server/test/features/imageService.test.ts` (B2)** — the "hands PORTERCLAUDE_AGENTS to the
  populate container" test now also asserts that a plain sync sets **no** force env and that
  `{force:true}` sets `PORTERCLAUDE_TOOLS_FORCE=1` (plus the log line). Regression guard.
* **`web/public/index.html` + `web/public/js/agents.js` (F1)** — the Sync button became a split
  button; the dropdown carries **Upgrade all agents (reinstall)**, which calls
  `syncAgents(true)` → `syncTools(hostId, true)` behind a `confirmDialog` explaining the cost.
  `syncAgents()` takes a `force` argument (default `false`); the plain button is unchanged.
  The Images panel's *Sync tools volume* button deliberately stays force-free.
* **`docs/design/api.md` (planner)** — the `POST …/images/tools/sync` section and the Agents
  section now describe `force:true` as the upgrade (image rebuild **and**
  `PORTERCLAUDE_TOOLS_FORCE=1`, no carry-over), `force:false` as "install what is missing".
* **`docs/AGENTS.md` §3 + troubleshooting, `docs/DEPLOYMENT.md` (O2)** — the wrong claim
  ("newly started ones get the new version") is replaced by a *Upgrading an agent to a newer
  release* subsection and one troubleshooting row.
* Mine: `docker/tools/README.md` (new *Upgrading an installed agent* section + the env-table
  row now names the switch and who sets it) and `install-agents.sh`, which logs
  `PORTERCLAUDE_TOOLS_FORCE=1: no carry-over, every agent is reinstalled from source` so the
  job log states plainly which of the two modes ran.

`docs/design/orchestration.md` §13.3/§13.6 needs no change — the image side already behaved as
specified; only the caller did not use it.
