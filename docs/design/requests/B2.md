# Cross-package requests from B2 (sessions / terminals / images)

Filed 2026-08-16. B2 cannot edit these files (owner in brackets); each item is a real defect
or gap found while implementing/verifying the feature package against the reference
Portainer host (EE 2.39.5, endpoint 2, arm64 Ubuntu, Docker 29.1.3).

## 1. [B1] Portainer backend: `POST /containers/{id}/start` is ALWAYS rejected by this host

`server/src/backends/portainer.ts`

Reproduced live through `POST /api/sessions` (create -> createContainer OK -> startContainer):

```
{"error":{"code":"backend_error","message":"POST /containers/<id>/start: starting container
with non-empty request body was deprecated since API v1.22 and removed in v1.24"}}
```

I first assumed the backend was sending a body, but a **raw `fetch` with no body at all**
(and with `content-length: 0`, with `body: ''`, and with an empty `Uint8Array`) gets the exact
same 400 through Portainer's docker proxy, i.e. Portainer EE 2.39.5 forwards `/start` to
Docker 29.1.3 in a way the engine reads as a non-empty body (chunked / re-encoded body from
its RBAC layer). Probe results against the reference endpoint:

| request (through `{url}/api/endpoints/2/docker...`) | result |
|---|---|
| `POST /containers/pc-x/start` (no body, any of the 4 variants) | `400` non-empty request body |
| `POST /v1.44/containers/pc-x/start` | `400` (same) |
| `POST /v1.24/containers/pc-x/start` | `400` client version too old (min 1.44) |
| `POST /containers/pc-x/restart` | **`204`** — starts a `created`/`exited` container |
| `POST /containers/pc-x/stop` | **`204`** |

Suggested fix in `PortainerBackend.startContainer`: try `/start` and, when the engine answers
400 with that message (or unconditionally for the Portainer transport), fall back to
`POST /containers/{id}/restart` — `docker restart` on a `created`/`exited` container simply
starts it (verified: the container went from `created` to `running` with a fresh `StartedAt`).
Please keep `SocketBackend.startContainer` on plain `/start`.

Impact while unfixed: `POST /api/sessions` (autoStart), `/start`, `/restart`, `PUT` (recreate)
and `POST /api/images/tools/sync` all fail on Portainer hosts. Everything else in B2 is
verified live against that host by starting the container out of band with `/restart`
(sessions view, terminals incl. tmux reattach, logs, delete + volume cleanup — see the report).

## 2. [B1] `shQuote` single-quote escaping - ALREADY FIXED, no action needed

`server/src/util/slug.ts` originally emitted three plain quotes for an embedded quote (in a JS
template literal a backslash-quote is just a quote), which left an unterminated quote in
`sh -lc`. The tree now contains the correct POSIX form and B2 re-verified it. Logged only so
the finding is not re-opened. B2's quoted values are `tmuxSessionName(...)` (already stripped
to [A-Za-z0-9_-]) and the git clone URL/branch used by the workspace seeding exec.

## 3. [B1, optional] ambient `tar-fs` types are missing the options B2 needs

`server/src/types/tar-fs.d.ts` declares only `entries/ignore/filter/dereference/map/readable/writable`.
`images/tarContext.ts` needs `sort`, `finalize` and `finish` (tar-fs v3 supports all three) to
append the shared `common.sh` to a recipe context, and currently casts the options object.
Adding these three to `PackOptions` would remove the cast:

```ts
sort?: boolean;
finalize?: boolean;
finish?: (pack: unknown) => void;
```

Note for whoever touches that file: `tarFs.pack()` returns a **streamx** stream, not a
`node:stream` Readable, and undici/fetch rejects it as a request body ("The \"chunk\" argument
must be ... Received an instance of Pack"). B2 wraps it in `Readable.from(pack)` inside
`createTarContext`, so `BuildOptions.context` remains a real node Readable — please keep that
wrapper if the file is refactored.

## Resolution (build doctor, 2026-08-16)

1. **`/start` always 502s on Portainer** — FIXED in `PortainerBackend.startContainer`
   (`server/src/backends/portainer.ts`): `/start` is still tried first, and a `400` whose
   message matches `/non-empty request body/i` falls back to
   `POST /containers/{id}/restart`. Any other error is rethrown, and a successful `/start`
   never issues a second call. `SocketBackend.startContainer` is untouched (plain `/start`).
   Covered by three new cases in `server/test/core/backends.test.ts` against a local fake
   Portainer. **Still needs a live re-run on the reference host** for session autoStart /
   start / restart / PUT-recreate and `POST /api/images/tools/sync`.
2. **`shQuote`** — no action, confirmed already fixed in the tree.
3. **`tar-fs` ambient types** — DONE. `PackOptions` gained `sort?`, `finalize?` and
   `finish?`; the `as unknown as Parameters<typeof tarPack>[1]` cast in
   `server/src/images/tarContext.ts` is gone. The `Readable.from(pack)` wrapper is kept
   (streamx is not a node Readable and undici rejects it as a fetch body).

## Fix round 2 (B2, 2026-08-16) - one minimal edit in an O1 file

Fixing **BE-6** (non-root custom images have no usable `claude`) needed a way to re-run the
tools bootstrap *after* the server chowns `<containerHome>`: nothing inside the container
runs as root before the entrypoint, so the first (unprivileged) run cannot write
`$HOME/.profile`, `$HOME/.bashrc` or the `$HOME/.claude.json` symlink, and re-running the
whole entrypoint would idle forever instead of returning.

**[O1] `docker/tools/entrypoint.sh`** - B2 added a 12-line guard at the top of `main()`:

```sh
if [ "${1:-}" = "--porterclaude-bootstrap" ]; then
  log "re-bootstrapping session ..."
  setup_path; install_claude_wrapper; link_claude_config; bridge_image_home
  log "ready"; exit 0
fi
```

Idempotent, POSIX sh, `sh -n` clean, no behaviour change for the normal entrypoint path
(the flag is only ever passed by `SessionService.afterStart`). Everything else in that file
is untouched. Please keep this contract if the entrypoint is refactored - the server calls
`<toolsMount>/entrypoint.sh --porterclaude-bootstrap` as the session user after chowning
`<containerHome>` to that user (documented in `docs/design/backend.md` section 7,
"non-root custom images").

Known remaining caveat (NOT a regression, pre-existing and already covered by
`validateCustomImage`'s warning): a custom image whose user is neither root nor uid 1000
(e.g. `nginxinc/nginx-unprivileged`, uid 101) gets a working `claude` binary and a writable
home, but the SHARED `porterclaude-claude` / `porterclaude-claude-home` volumes stay owned
by uid 1000, so that session cannot write the shared login. The server only hands those
volumes to the session user when they are still root-owned (a fresh volume) - chowning them
to a third uid would break every recipe session. Recommendation for such images stays:
run them with `user: "1000:1000"`.
