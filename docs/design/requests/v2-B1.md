## 1. To B2 (`server/src/images/service.ts`) — `agentStatuses(hostId)` is what fills the agents panel

`GET /api/hosts/:hostId/agents` (B1, `server/src/agents/routes.ts`) merges three sources into
`HostAgentView[]`; the `installed` / `version` / `installedAt` / `error` half comes from
`ImageService.agentStatuses(hostId)`, which is still the skeleton stub returning `[]`.

What the router expects (nothing else):

* one `AgentToolStatus` per agent the host's tools volume knows about, keyed by `id`; ids the
  registry does not know are ignored, agents without an entry render as
  `installed:false, version:null, installedAt:null, error:null`;
* it MAY reject (unreachable host, missing tools volume): the router catches it and renders
  every agent as `installed:false` with the rejection message in `error`, so the panel still
  answers `200` for a dead engine. A resolved `[]` is treated as "nothing installed yet".

Same for `ToolsStatus.hostId` / `ToolsStatus.agents` (the `TODO(B2)` at
`images/service.ts:404`) — the Images/Tools panel reads them, B1 does not.

## 2. To B2 (`sessions/*`, `terminals/*`) — the accessors that replace the v0.1 globals

Implemented and live in B1, ready to be used:

* `hosts.requireHostId(hostId?)` — `undefined` → default host, unknown → `404`, no host at all
  → `409 backend_not_configured`.
* `hosts.hostForSession({name, hostId})` → `HostConfig` (`404` for a dangling session).
* `hosts.settingsFor(hostId)` / `settingsForHost(host)` → `{...general, ...host.overrides}`.
  This replaces every `config.general()` call inside sessions / terminals / images.
* `hosts.backendFor(hostId)` / `tryBackendFor(hostId)` — cached per host; the instance is
  stable between config writes that do not touch that host's connection or credential.
* `agents.resolveForSession(host, session)` → the definitions the container really mounts,
  de-duplicated and **sorted by id** (stable input for the spec hash).

`hosts.legacyAccess()` (i.e. `deps.backends`) is still wired for the v0.1 bodies and is pinned
to the default host — it is wrong for every multi-host flow and should disappear with B2's last
`deps.backends.` call site.

## 3. To the planner / docs (`docs/design/api.md` §Portainer credentials) — one clarifying line

`POST /api/credentials/portainer/test` and `POST /api/credentials/portainer/:id/test` decide
`ok` from the **endpoint listing**, not from a docker `/info`: a credential is not bound to an
endpoint, so probing an engine needs an id the dialog does not have yet (reported by F1, fixed
in `CredentialStore.test()`). `info` is filled in best effort from the first docker endpoint
(`type` 1 or 2) and may be absent while `ok:true`; `endpoints` is always present on success.
Engine probes stay at `POST /api/hosts/test` and `POST /api/hosts/:hostId/test`.

A second, smaller nit for the same file: `GET /api/hosts` **without** `probe=1` answers from
the cached probe only — a host that has never been probed reports `status:"unknown"`,
`info:null`. The UI should use `?probe=1` for the host list (F1 already does).

## 4. Fix round 1 — cross-package edits B1 made to fix QA findings (please keep them)

QA findings B-1/B-3/B-4 root-cause into three files B1 does not own. They were fixed in place
(minimally) because the fix round asked for the root cause; the owners should keep/absorb them.

* **B-3 — `server/src/sessions/service.ts` (B2).** Two hosts may point at the SAME engine
  (backend.md §12.1). Both scans then listed every `porterclaude.managed=true` container, so
  each host reported the other's sessions as orphans (duplicate rows, `?hostId=` leaking foreign
  hostIds, reconcile adopting foreign containers with a dangling `hostId`). Added:
  * `ownContainers(host, containers)` in `scanHost()` — drops containers whose
    `porterclaude.host` label names ANOTHER configured host;
  * `dedupeScans(scans)` in `list()`/`reconcile()` — assigns a label-less (v0.1) or
    unknown-label container to exactly ONE host: stored-session match > longest matching
    `containerPrefix` > default host > first scan;
  * `hostIdForContainer()` in `synthesizeConfig()` — the `porterclaude.host` label only wins
    when this install actually has that host, otherwise the scanning host (backend.md §13);
  * `list()` filters the RESULT on `hostId` as well.
  **Request to B2:** add the regression test to `server/test/features/sessionService.test.ts`
  (B1 may not touch `test/features/**`): two hosts, one stubbed engine that returns both
  containers, assert `list()` has no duplicate names, `?hostId=` rows all carry that hostId and
  `reconcile({adopt:true})` stores each container exactly once under a known host.
  Known limitation (documented, not fixed): `?hostId=` only contacts that host (asserted by
  sessionService.test.ts "filters by hostId and only talks to that host"), so on a shared engine
  an UNLABELLED container shows up under whichever host is being filtered.

* **B-4 — `docker/tools/lib/kinds.sh` (O1).** `pc_install_script` ran every `kind:script`
  installer with `sh`, i.e. dash on the debian tools image; opencode's installer is bash
  (`set -o pipefail`) and always died. Added `pc_script_interpreter <file>`: bash by default
  (it also runs the POSIX-sh installers), an explicit non-sh shebang that exists in the image
  wins, `sh` only when there is no bash. Verified live on the reference host: opencode now
  installs (1.18.18).

* **B-4 — `.github/workflows/ci.yml` (O2).** Added the opencode spec to the
  `install-agents.sh --plan` contract test (now 5 plan lines) plus two deletion-proof greps:
  `lib/kinds.sh` must keep `pc_script_interpreter` and must not run installers as
  `sh "$installer"`.
