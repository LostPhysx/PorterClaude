## 1. `golden-layout` has no `bundle/` build - see requests/F2.md item 1 (no action needed from F1)

**Status: resolved by F2; kept here only as corroboration.**

Independently verified against the published npm tarball (not just our `node_modules`):
`golden-layout@2.6.0` - the latest release - contains no `dist/bundle/` directory, so
neither `/vendor/golden-layout/bundle/esm/golden-layout.js` (api.md, frontend.md section 2)
nor the "UMD twin" fallback that frontend.md offers exists. `dist/esm/**` is real ESM but
uses extensionless relative specifiers.

F2 already works around this in `code.js` and asks B1 for
`express.static(dir, { extensions: ['js'] })` in `server/src/vendor.ts` (requests/F2.md
item 1). F1 confirms that fix works: with `extensions: ['js']` on the vendor mount,
`GET /vendor/golden-layout/esm/ts/golden-layout` returns the `.js` file and the whole graph
loads natively. The remaining F1-adjacent piece is a **doc correction** (planner): the
concrete-URL lists in `docs/design/frontend.md` section 2 and `docs/design/api.md`
("Static assets") should point at `/vendor/golden-layout/esm/index.js` and drop the
non-existent `bundle/umd` fallback sentence. `web/tools/verify-assets.mjs` (F1-owned)
currently passes because `code.js` no longer uses a static import for it.

per-file `/* global … */` pragmas (`api.js`, `app.js`, `util.js`, `sessions.js`,

sessionStorage, location, navigator, history, setTimeout, clearTimeout, setInterval,

## 3. Confirmations wanted on api.md items (no code change expected)

* `GET /api/images` — F1 reads image refs from `images[].repoTags` (falling back to
  `RepoTags`) to fill the custom-image datalist. Please confirm the field name that
  `ImageSummary` actually uses.
* `GET /api/docker/networks` — F1 reads `networks[].name` (falling back to `Name`).
* `POST /api/images/recipes/:name/build` returning `409 conflict` while a build runs:
  F1 recovers by re-reading `GET /api/images/recipes` and using the recipe's `jobId`, then
  `GET /api/images/jobs` as a second fallback. Keeping `jobId` populated on the recipe
  while `building: true` is what makes the "open the running job instead of erroring"
  behaviour work.
* `GET /api/images/tools` — F1 uses `status.jobId` the same way while `syncing: true`.

## 4. Bug found while exercising the UI against the reference host (owner **B2**)

`POST /api/sessions` fails at the start step with a Docker error, so a session can never be
created (the container is created, the start fails, and the rollback removes it again):

```
DockerApiError: POST /containers/<id>/start: starting container with non-empty request body
was deprecated since API v1.22 and removed in v1.24
```

Reproduced through the UI (custom image `alpine:3.20`, volume workspace) against the
reference Portainer host with the current `server/src` working tree; the UI surfaced it
correctly as a `502 backend_error` in `#session-form-error`. Fix: send `/containers/{id}/start`
with **no** body (or `Content-Length: 0`) in the backend's `startContainer`. This is the only
thing blocking the "create → row appears → start/stop/logs/destroy" acceptance run for F1's
Sessions tab; every other lifecycle path was verified against the real engine.

Also observed while validating a custom image: `POST /api/images/custom/validate` reported
`ok:true` for `alpine:3.20` together with the warning "could not run a shell in this image"
- the UI renders both, no change requested, just flagging it in case the probe is meant to
downgrade `ok` in that case.

## Resolution (build doctor, 2026-08-16)

1. **golden-layout has no `bundle/`** — docs corrected (see B1.md item 3 / F2.md item 2), and
   `extensions: ['js']` is now set on the vendor mounts, so the native fast path works:
   verified live that `GET /vendor/golden-layout/esm/ts/golden-layout` and
   `.../esm/ts/config/config` return `200 text/javascript`.
2. **eslint globals** — DONE. `eslint.config.js` carries the full frontend.md 1.1 browser
   globals map plus a Node-globals block for `web/tools/**/*.mjs`. All nine
   `/* global ... */` pragmas were removed from `web/public/js/*.js` and
   `web/tools/verify-assets.mjs`; `npm run lint` and `npm run verify --workspace web` are green.
3. **Field-name confirmations** —
   * `GET /api/images`: the field is **`tags`**, not `repoTags` (`ImageSummary` in
     `server/src/backends/types.ts`). `web/public/js/sessions.js` read
     `img.repoTags || img.RepoTags`, so the custom-image datalist was always empty; fixed to
     `img.tags || img.repoTags || img.RepoTags`.
   * `GET /api/docker/networks`: `networks[].name` — **confirmed correct**.
   * `recipe.jobId` / `tools.status.jobId` are populated while `building` / `syncing`
     (`server/src/images/service.ts`), and the `409` body carries `{ jobId }` in `details` —
     the "open the running job" recovery works as F1 implemented it.
4. **`/containers/{id}/start`** — fixed on the Portainer transport, but not by removing a
   body (the backend never sent one): Portainer's proxy itself is what the engine sees as a
   non-empty body, so the transport now falls back to `/restart`. See B2.md item 1.
