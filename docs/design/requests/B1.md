# Cross-package requests from B1 (backend core)

## 1. B2 — `server/src/images/tarContext.ts` does not typecheck (blocks `npm run typecheck`)

```
server/src/images/tarContext.ts(17,11): error TS2430: Interface 'TarPack' incorrectly extends
interface 'Readable'. The types returned by 'destroy(...)' are incompatible between these
types. Type 'void' is not assignable to type 'this'.
```

`node:stream`'s `Readable.destroy(err?: Error): this`, so the override in `TarPack`
(`destroy(err?: Error): void`) is illegal. It is the only remaining typecheck error in the
server workspace; everything B1 owns is clean.

Suggested fix (one line, inside B2's file):

```ts
interface TarPack extends Readable {
  entry(header: { name: string; size: number; mode?: number; type?: string; mtime?: Date },
        buffer: Buffer, callback?: (err?: Error | null) => void): unknown;
  finalize(): void;
  // drop the destroy() override entirely -- Readable already declares it
}
```

B1 owns `server/src/types/tar-fs.d.ts` and can widen the declared return type of
`tar-fs`'s `pack()` if B2 prefers that instead — say the word and it will be changed to a
named `Pack` interface exported from the ambient module.

## 2. QA plan — login throttle ordering (docs, no code change)

`qa_plan` steps 3 and 4 conflict: step 3 spends all 10 login attempts on wrong passwords
(the 11th is answered `429 rate_limited`, as specified), so the *correct* login in step 4
is still throttled for the rest of the 15 minute window. The throttle deliberately runs
**before** the password is checked (checking first and only throttling failures would let
an attacker brute force at will). Either restart the server between the two steps (the
limiter is in-memory) or run step 4 before step 3. `skipSuccessfulRequests` is enabled, so
successful logins never consume the budget.

## Fix round 1 (QA BE-1) — doc line in `docs/design/backend.md` is now stale

`docs/design/backend.md:97` still says:

```
6. `new BackendManager({config, env, log})`; `config.on('change', () => backends.invalidate())`.
```

That is exactly the bug QA filed as BE-1: `ConfigStore` emits `change` for *every* write
(UI layout autosave ~1.5 s, session writes, password change), and rebuilding the backend
there tore down the Portainer keep-alive transport used by in-flight builds/pulls/execs.
`server/src/index.ts` now uses the fingerprint-guarded variant:

```
6. `new BackendManager({config, env, log})`; `config.on('change', () => backends.invalidateIfChanged())`
   -- only a change to backend.kind / portainer.{url,endpointId,insecureTls,apiKeyEnc} /
   socket.socketPath rebuilds the transport. `PUT /api/settings/backend` still calls the
   unconditional `invalidate()`.
```

Whoever owns `docs/design/backend.md` (not B1) should update that line; no code change is
required in any other package.
