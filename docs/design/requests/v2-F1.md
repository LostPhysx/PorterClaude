### Original report: "Test" on a Portainer credential probed a docker endpoint that does not exist

`CredentialStore.test()` builds `{ type: 'portainer', …, endpointId: 0 }` and hands it to
`testConnection()`, which calls the **docker `/info` of endpoint 0**. A credential is not
bound to an endpoint at all, so on a normal Portainer this always fails:

```
POST /api/credentials/portainer/portainer-1/test  ->
{"ok":false,"error":{"code":"backend_error",
 "message":"GET /info: Unable to find an environment with the specified identifier inside the database"}}
```

Verified live against the reference Portainer (EE 2.39.5, the only endpoint there is id `2`);
`GET /api/credentials/portainer/portainer-1/endpoints` with the same stored key answers
`200 {"endpoints":[{"id":2,…}]}`, i.e. the key is fine — only the probe target is wrong.

**Ask**: make the credential test validate the *credential*, not an engine — e.g.
`GET /api/status` (`PortainerBackend.portainerStatus()`) plus `listEndpoints()`, and return
`{ ok: true, endpoints }` (no `info`). Probing an engine is what `POST /api/hosts/test` and
`POST /api/hosts/:hostId/test` are for, and both already work.

**Impact while it lasted**: the credentials dialog's `Test` button reported a red
`backend_error` for a perfectly good key. `hosts.js` renders whatever `BackendTestResult` the
server returns (success = the endpoint count + the engine table), so nothing had to change on
the UI side once the server was fixed.

## 2. To the planner / F2 (documentation nit, no code change) — `hosts.js` and the agent registry

`docs/design/frontend.md` §12.2 draws the module graph as acyclic with `hosts.js ─▶ api/util/bus`,
but the skeleton's TODO in `renderHosts()` asks for the host table's agent chips to be labelled
"through agents.js `agentLabel()`". `agents.js ─▶ images.js ─▶ hosts.js`, so a
`hosts.js ─▶ agents.js` import would close a cycle — exactly the one the two stated rules exist
to prevent.

Implemented instead (no import): `hosts.js` keeps its own copy of the registry, seeded from
`GET /api/agents` on panel entry and refreshed from the `agents:changed` bus event, and labels
the chips from that. Same rendering, graph unchanged. Worth a one-line correction in §12.2/the
skeleton comment so a reviewer does not read it as a missing feature.

Note for the same reason: `hosts.js` **does** import `GENERAL_FIELDS`/`getSettings` from
`settings.js` (the brief mandates it — the per-host overrides form is the General field list),
which makes `settings.js ↔ hosts.js` a deliberate back edge. To keep module evaluation order
irrelevant, `settings.js` now resolves its panel map lazily (`panels()` instead of a top-level
`const PANELS`); every cycle edge is function-scoped, so no binding is read during evaluation.
