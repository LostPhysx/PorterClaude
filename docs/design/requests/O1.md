## 1. To O2 (.github/workflows/ci.yml) — `package-lock.json` IS committed

The planner assumed the lock file was absent ("do not enable setup-node's npm cache").
It exists in the tree today (`package-lock.json`, 207 KB, tracked), and
`python deploy/lib/dockerignore.py --root .` lists it, so it reaches every build context.

Consequences:

  (`if [ -f package-lock.json ]; then npm ci; else npm install; fi`) — no change needed there;
  with the lock present it uses `npm ci`.
* ci.yml can now enable `cache: npm` in `actions/setup-node` and use `npm ci` unconditionally.
  Purely an optimisation; the current "fallback" wording is just stale.

## 2. To B2 (server/src/images/service.ts) — reading the exact Claude Code version

Recipe images write the exact `claude --version` to `/etc/porterclaude/claude-version` and
the recipe name to `/etc/porterclaude/recipe`; the tools volume carries `<toolsMount>/VERSION`.
The `porterclaude.claude-version` **label** only ever holds the *requested* build arg
(`latest` / `stable`), because the classic builder cannot turn `RUN` output into a label.
Prefer the file whenever a container is available, and treat the label as a hint.
(Already noted in the planner's cross-topic notes — repeated here for traceability.)

## 3. To B2 — php sessions and `PC_HTTP_PORT`

The php recipe binds port 80 as uid 1000, which works on a normal dockerd
(`net.ipv4.ip_unprivileged_port_start=0`). Where it does not, the session env var
`PC_HTTP_PORT` (any port) makes nginx listen there instead; the published port has to match.
No API change is required — it is an ordinary session env var — but the Sessions UI hint for
the php recipe could mention it.

## Fix round 1 (O1) — changes made outside `docker/**`

Two one-line touches in files O1 does not own. Both are the *same* defect class as OPS-1
(a `data`-prefixed DATA_DIR inside the checkout being matched too narrowly); flagging them
here so the owners can absorb them.

### a. `eslint.config.js` (O2) — `data/**` → `data*/**`

`npm run lint` at the repo root went red (8961 problems) as soon as another agent dropped
ad-hoc scripts into `data.qa.frontend/qa/*.mjs`: the ignore list only had `data/**`, so
every DATA_DIR that is not literally named `data` was linted as project source. Changed to
`data*/**`, matching the prefix convention that `.gitignore`, `.dockerignore`,
`deploy/deploy.sh` and `docs/DEPLOYMENT.md` already key off. Lint is green again.

### b. `docs/design/orchestration.md` §4.4 step 1 — how `IMAGE_HOME` is derived

The spec said "IMAGE_HOME (from `$HOME`, else the passwd entry of `id -u`)". That was
written before the OPS-3 fix pinned `HOME=<containerHome>` in the container env. With the
pin in place `$HOME` is the *server's* answer, not the image's, so `IMAGE_HOME == HOME`,
and step 6 (the image-home bridge) silently became dead code — `su -` / `sudo -i` /
`getpwuid()` callers still landed in an unlinked `/root`. The doc now says: when
`PORTERCLAUDE_HOME` is set, read passwd; only without it does `$HOME` win.
`docker/tools/entrypoint.sh` implements exactly that.
